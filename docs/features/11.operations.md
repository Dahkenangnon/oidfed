# 11. Operating a federation application

A successful trust check still depends on the host’s storage, network policy, clock, and operational controls. The library exposes contracts for those services so each deployment can supply them. [Federation §§17–19](https://openid.net/specs/openid-federation-1_0.html#section-17).

Connect durable storage and federation keys to the host, and connect protocol-specific replay stores and callbacks to the appropriate role. Configure transport and logging in those same options so the operation that uses them also produces the expected diagnostics and failures.

## Operate the same workflow across processes

The examples run in one process so the trust relationships are easy to inspect. A deployment adds durable keys, authoritative storage, shared replay decisions, HTTPS routing, network limits, and observability. Decide which component owns each before distributing the service across workers.

Before going live, check that a participant can validate a Trust Chain to the intended Trust Anchor through the public HTTPS endpoints. Exercise a denied caller, expired evidence, and a worker restart. Workers serving the same authority need access to the same authoritative records and shared replay state. Keep enrollment and accreditation records in durable storage. Cancellation should release a waiting caller without corrupting a write already owned by storage.

Finally, use host-supplied logging to identify failed stages and configuration recommendations. Keep those messages separate from the result that controls acceptance. An unavailable log sink must not decide whether a chain, proof, or registration is accepted.

## Deployment operations

The following are deployment recommendations. The linked sections explain the protocol concerns behind them. They do not prescribe backup systems, monitoring tools, or clock-synchronization services.

- Restrict access to private keys, registration secrets, and administrative mutation paths. [Federation §3.1.1](https://openid.net/specs/openid-federation-1_0.html#section-3.1.1) defines published federation JWKS as public keys. Follow oidfed's [key custody contract](11.6.storage-adapters.md#keys): keep private material behind the provider and out of authority records and published metadata.
- Back up authoritative storage and key-provider state. Test recovery of historical public keys, event histories, registration deadlines, and replay state without allowing accepted proofs to be replayed. Plan recovery around oidfed's [storage guarantees](11.6.storage-adapters.md); the specifications define no backup protocol.
- Synchronize clocks across serving processes. [Federation §10.2](https://openid.net/specs/openid-federation-1_0.html#section-10.2) requires time checks; [JWT §4.1.4](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.4) permits small leeway for clock skew. Account for the configured acceptance window when retaining replay records and scheduling expiry and rollover.
- Monitor refresh failures, snapshot age, signing failures, replay-store errors, and expiring evidence using oidfed's [refresh](14.2.collection-operations.md#refresh-and-storage) and [replay](11.6.storage-adapters.md#replay-protection) contracts. Follow [Federation §11.3](https://openid.net/specs/openid-federation-1_0.html#section-11.3) when handling persistent independent-key mismatches. Choose alert thresholds for your deployment.
- Define how to respond to key compromise and loss of authoritative state, including recovery procedures. The framework chooses any additional federation revocation process under [§11.4](https://openid.net/specs/openid-federation-1_0.html#section-11.4).
- Limit published Entity Statements to organizational information needed for federation, following [§19.1](https://openid.net/specs/openid-federation-1_0.html#section-19.1). Consider the tracking risks of Trust Mark Status and Fetch requests and the mitigations discussed in [§19.2](https://openid.net/specs/openid-federation-1_0.html#section-19.2) and [§19.3](https://openid.net/specs/openid-federation-1_0.html#section-19.3).
