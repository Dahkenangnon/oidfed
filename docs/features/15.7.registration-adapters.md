# 15.7. Add application-specific registration checks

[Feature guides](README.md) / [15. OIDC and OAuth workflows](15.oidc-and-oauth.md) · [Example context](15.oidc-and-oauth.md#example-context)

**Umeå University OP**'s OP engine needs a profile-specific client setting in its registration record. It can adapt federation-validated metadata before preparing the registration response.

## How to use it

Set `registrationProtocolAdapter` on `OidcProviderRole` or `OAuthAuthorizationServerRole`. The shared `RegistrationProtocolAdapter` contract has a synchronous validation method and a response-enrichment method. The handler first performs federation validation. The adapter can reject unsupported profile metadata and receives optional peer-resolved OP context where available. [Registration processing](https://openid.net/specs/openid-federation-1_0.html#section-12.2.2); [Response](https://openid.net/specs/openid-federation-1_0.html#section-12.2.3).

```ts
import { ok } from "@oidfed/core";
import { OidcProviderRole, type OidcProviderRoleConfig, type RegistrationProtocolAdapter } from "@oidfed/oidc";

export const umeaOpAdapter: RegistrationProtocolAdapter = {
  validateClientMetadata(raw) {
    // Add the host profile's checks here; federation validation already ran.
    return ok(raw);
  },
  enrichResponseMetadata(metadata) {
    return { ...metadata, "urn:academic:registration-profile": "umeaOp-v1" };
  },
};

export function umeaOpRole(config: OidcProviderRoleConfig) {
  return new OidcProviderRole({ ...config, registrationProtocolAdapter: umeaOpAdapter });
}
// Attach this fresh role to UmeaOp's Leaf or Authority before processing registrations.
```

## What your application owns

The example extension is a fictional host convention. Output must still satisfy federation policy and protocol metadata rules. Keep enrichment free of irreversible acceptance side effects; use `beforeRegistration` for an accreditation rejection before side effects. The host persists clients and handles secrets through the configured integration, not by expecting an adapter to create an OP database automatically.

With `registrationManagement: "read-only"` on the provider role, enrichment may also return `registration_access_token` and `registration_client_uri` together. They must pass response validation and federation policy. Without that opt-in, both fields are removed. See [read-only registration access](15.3.oidc-explicit-registration.md#let-the-rp-read-its-registered-metadata) for the host's endpoint and token responsibilities.

## Keep validation separate from persistence

Use the adapter to interpret protocol metadata and enrich the response within the accepted profile. Put an accreditation rejection in the pre-registration gate when it must run before downstream acceptance effects. The declarative requirement runs before the optional callback, so a callback cannot override a failed requirement.

Treat adapter errors as a failed registration and leave the client store consistent. A host callback that throws or rejects must not become a successful partial registration. Test your integration with both a rejected policy and an unavailable persistence layer; these failures happen at different stages and need different recovery.

## Implement a protocol adapter

Implement `RegistrationProtocolAdapter` to add profile checks or enrich explicit registration responses. This example adds one profile rule; compose it with `OIDCRegistrationAdapter` if you also need its OIDC schema checks.

In explicit processing, `validateClientMetadata` receives the resolved metadata map. Its successful returned map is used before response enrichment, and the optional `context` can include validated peer-chain metadata.

In automatic processing, the same hook receives the selected client block. It controls acceptance, but returning changed metadata does not rewrite the authenticated automatic-registration result. The example handles both input shapes. `enrichResponseMetadata` receives the selected client block and applies to the explicit response.

```ts
import type { RegistrationProtocolAdapter } from "@oidfed/oidc";
import { federationError, FederationErrorCode, ok, err } from "@oidfed/core";

const customAdapter: RegistrationProtocolAdapter = {
  validateClientMetadata(raw, context) {
    const metadata = Object.hasOwn(raw, "openid_relying_party")
      ? raw.openid_relying_party : raw;
    const contacts = metadata && typeof metadata === "object" && !Array.isArray(metadata)
      ? (metadata as Record<string, unknown>).contacts : undefined;
    if (!Array.isArray(contacts) || contacts.length === 0 ||
        !contacts.every(contact => typeof contact === "string")) {
      return err(federationError(
        FederationErrorCode.InvalidMetadata,
        "A nonempty contacts list is required by this federation profile",
      ));
    }
    return ok(raw);
  },
  enrichResponseMetadata(rpMeta, trustChain, context) {
    return {
      ...rpMeta,
      client_id: trustChain.entityId,
      custom_enriched_field: "enriched-value",
    };
  },
};
```

## Require accreditation before registration

`OidcProviderRole` supports `trustMarkRequirements` and `beforeRegistration` for automatic and explicit registration. `OAuthAuthorizationServerRole` exposes the same policy for its automatic and explicit flows. Either option can stand alone. When both are set, requirements run first; the callback runs only if they pass, and both must accept.

```ts
import { OidcProviderRole, type OidcProviderRoleConfig } from "@oidfed/oidc";
import { type ValidatedTrustChain, type Result } from "@oidfed/core";

export async function createAccreditedProvider(providerConfig: OidcProviderRoleConfig, applicationAccreditationPolicy: (chain: ValidatedTrustChain, registrationType: "automatic" | "explicit") => Result<void> | Promise<Result<void>>) {
  const provider = new OidcProviderRole({
    ...providerConfig,
    trustMarkRequirements: { requiredTypes: ["https://edugain.example/marks/research-service"] },
    beforeRegistration: async ({ chain, registrationType }) => {
      return applicationAccreditationPolicy(chain, registrationType); // Result<void>
    },
  });
  return provider;
}
```

The callback receives frozen authenticated chain evidence. Rejection, an exception, or a malformed result stops registration before persistence, response signing, or replay consumption. Requirements recheck mark, delegation, issuer-proof, and historical-evidence deadlines. Use the shared `options.trustMarkVerification` configuration to establish the required issuer evidence; a valid RP chain alone does not guarantee verified accreditation. A fresh Status request remains a separate application policy choice.
