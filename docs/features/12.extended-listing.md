# 12. Extended Subordinate Listing

[Feature guides](README.md)

**eduGAIN** needs to inspect registrations in manageable pages. Extended Listing adds cursors, filters, timestamps, and selected claims to that operator workflow. [Extension: Draft 03](https://openid.net/specs/openid-federation-extended-listing-1_0-03.html).

For its own records, an operator calls `TrustAnchor.listSubordinatesExtended()` or `Intermediate.listSubordinatesExtended()`. Configure and advertise the endpoint for other applications; a remote caller uses core's Extended Listing client.

## Read a directory in manageable pages

eduGAIN can expose more enrollment information than a basic list of identifiers. A client selects claims, applies supported filters, and follows pages with an opaque cursor. This supports operator directories and synchronization tasks without requiring each client to understand the storage adapter.

Choose the minimum useful claims for the task and keep the query consistent across pages. Optional timestamps help a client understand recorded changes; custom fields and filters require a shared federation definition. The server's configured capabilities still determine which requests are accepted.

Use the returned identifiers as discovery input when the application needs to trust a participant. A directory entry does not replace the current signed chain. For a dashboard, distinguish a listed participant from one whose chain and protocol metadata have just been validated, and show retrieval or validation failures without quietly hiding their meaning.

## Work through this topic

Carry opaque continuation values forward with the same query. A listing helps locate records; consumers still validate the evidence they rely on.

## Extended Listing, Draft 03

The authority handler implements the `from` and claim-selection rules in [§3.2](https://openid.net/specs/openid-federation-extended-listing-1_0-03.html#section-3.2) and the opaque `next` pointer in [§3.3](https://openid.net/specs/openid-federation-extended-listing-1_0-03.html#section-3.3). Responses `MUST` use consistent ordering under [§3.1.1](https://openid.net/specs/openid-federation-extended-listing-1_0-03.html#section-3.1.1). Implementations choose the ordering key. oidfed's [storage contract](11.6.storage-adapters.md#subordinates) uses lexicographic Entity Identifier ordering and an inclusive first-unreturned cursor.

The time filters in [§3.2](https://openid.net/specs/openid-federation-extended-listing-1_0-03.html#section-3.2) and audit fields in [§3.3](https://openid.net/specs/openid-federation-extended-listing-1_0-03.html#section-3.3) need accurate registration and update times. oidfed's adapter contract requires maintaining those timestamps and applying repository filters before pagination. Repeated Trust Mark types use OR matching, as required by §3.2. Direct writes must supply or maintain the fields required by the [subordinate storage contract](11.6.storage-adapters.md#subordinates).

Choose limits that allow the endpoint to return the requested claims, following [§3.1.2](https://openid.net/specs/openid-federation-extended-listing-1_0-03.html#section-3.1.2). Configure authentication through the endpoint's advertised methods. [§3.2](https://openid.net/specs/openid-federation-extended-listing-1_0-03.html#section-3.2) uses the base List endpoint's authentication rules.

[Federation §8.2.1](https://openid.net/specs/openid-federation-1_0.html#section-8.2.1) defines the `trust_marked=true` filter and leaves the false case unspecified. As library policy, oidfed treats `false` as adding no restriction. Supplied mark-type filters still apply. See the [Extended Listing configuration](12.1.extended-listing.md#server-filters-claims-and-pagination-limits) for optional features and defaults.
