# 14. Entity Collection

[Feature guides](README.md)

**Maya's wallet** needs a useful directory of credential issuers for **Maya**. **Driving Licence Federation** can serve a collection snapshot so the wallet can find candidates without walking the whole graph for every search. [Extension: Draft 01](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html).

Attach `collection` to an Authority or Leaf, then use the host's `.collection` service for scheduled refreshes and queries. Its `handleRequest()` serves the advertised endpoint. Independent directories without a federation host can use core's standalone collection service.

## Build a searchable snapshot

An Entity Collection provider gathers information about participants and publishes a filtered snapshot for search. eduGAIN might expose universities by display name; Driving Licence Federation might expose credential issuers that meet its accreditation policy. The collector, snapshot store, refresh schedule, and HTTP service can be configured independently.

Refresh validates the collected inputs and applies the provider's publication choices. Search reads the stored snapshot. This separation prevents every anonymous search from starting a fresh traversal of the federation. Custom collectors and query matchers still need to respect the same ingestion and response contracts.

A returned entry is unverified information for the consumer's purposes. Use it to find a candidate, then establish trust for registration, credential issuance, or presentation. The collection's verification work supports its directory policy; it does not replace the relying application's own anchors and acceptance rules.

## Work through this topic

Schedule collection refresh and preserve snapshot consistency. Directory entries are informational; establish trust in the selected participant before using its metadata.

## Entity Collection, Draft 01

[§5.1](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-5.1) and [§5.3](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-5.3) leave collection methods and additional scope restrictions to implementations. The operator selects supported anchors and scope. Under [§5.2](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-5.2), implementations `SHOULD` consider Entity Configuration information when populating response claims and `MAY` use additional information.

oidfed's default collector validates chains against pinned anchors. To use other sources or impose additional restrictions, provide a custom collector or refresh-time filter under the [collection policy contract](14.2.collection-operations.md#collection-policy). Custom collectors manage their input sources and eligibility deadlines.

[`EntityCollectionService`](../../packages/core/src/entity-collection/service.ts) serves stored snapshots. Your application schedules `refresh()`; requests do not start traversal. The service serializes refreshes for each anchor within one instance. The [store contract](../../packages/core/src/entity-collection/types.ts) requires atomic publication but does not serialize refresh work across processes.

If multiple writers need ordered publication, choose a coordination mechanism, such as one scheduled writer per anchor or an external lock. [§5.1](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-5.1) leaves the implementation open. It does not prescribe snapshots, a refresh interval, or a distributed scheduler.

Responses `MUST` use consistent ordering under [§3.1.1](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-3.1.1). [§3.3.1](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-3.3.1) defines continuation requests and unavailable cursors. oidfed's [refresh and storage contract](14.2.collection-operations.md#refresh-and-storage) requires storage implementers to provide atomic publication, anchor isolation, detached reads, and snapshot/cursor retention.

oidfed keeps the previous snapshot after an incomplete refresh and bounds optional issuer lookups as part of its availability policy. Operators choose refresh frequency. Monitoring failures and snapshot age is deployment guidance.

Authentication follows [§3.3.1](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-3.3.1) and [Federation §8.8](https://openid.net/specs/openid-federation-1_0.html#section-8.8). The configured replay store and memory fallback are [oidfed integration choices](14.2.collection-operations.md#authentication-and-http-clients). The memory store does not protect against replay across processes.

[§6.1](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-6.1) requires clients to treat unsigned results as informational and returned Trust Marks as unverified. Perform federation trust validation of selected entities and verify marks before relying on them, even if the collector checked them during refresh.
