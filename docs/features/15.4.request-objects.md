# 15.4. Create and process OIDC Request Objects

**LIGO Wiki**'s signed authorization request can be too large for a convenient redirect query. The RP chooses how **Umeå University OP** receives it while preserving the same signed protocol content.

## How to use it

OIDC supports `form_post`, query, and `request_uri` delivery. `form_post` is the default. For `request_uri`, the RP supplies a URL and serves the returned JWT itself with the required media type; the library does not host it. The OP role processes the received signed JWT. [Request Objects](https://openid.net/specs/openid-federation-1_0.html#section-12.1.1.1).

```ts
import type { OidcProviderRole } from "@oidfed/oidc";

export async function acceptLigoWikiRequest(op: OidcProviderRole, jwt: string) {
  const result = await op.processAutomaticRegistration(jwt);
  if (!result.ok) return result;
  return result; // Continue with the OP engine only after federation processing succeeds.
}
```

## What your application owns

Own request hosting, lifetime, session binding, and any one-use delivery policy. Configure protocol signing keys and replay storage; do not use an arbitrary decoded Request Object as a validated registration result. Malformed chain headers are errors. This layer does not automatically implement every authorization transport such as a complete PAR endpoint; integrate such protocol features through the host engine.

## Bind the request to the intended recipient

Build the Request Object from the metadata and keys for the selected federation path. If the operation uses contextual policy, validate the actual authenticated request values against that context rather than assuming a previous discovery covered every later request.

Use the protocol transport that your OP supports and preserve its parameters. Do not copy OIDC-specific outer-parameter rules into an OAuth-only flow. A modified request must be signed again; changing a saved JWT payload after validation does not preserve either its signature or the accepted replay identity.
