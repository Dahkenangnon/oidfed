# 7.5. Authenticate federation endpoint clients

**Umeå University** allows public listing but requires authentication for selected operations. A caller's ability to reach an endpoint must not silently grant it the authenticated path.

## How to use it

Authority metadata advertises the accepted methods per endpoint. The built-in shared layer supports `none` and `private_key_jwt`; advertised methods without a built-in or registered verifier fail construction. `private_key_jwt` needs a replay store and a trusted client federation-key lookup, defaulting to registered subordinate keys. [Endpoint authentication](https://openid.net/specs/openid-federation-1_0.html#section-8.8).

<!-- oidfed-example -->
```ts
import type { CryptoEngine, RotatingKeyring } from "@oidfed/crypto";
import type { AuthorityConfig } from "@oidfed/authority";
import type { FederationStorage } from "@oidfed/core";

export function protectedUniversityConfig(
  engine: CryptoEngine,
  keys: RotatingKeyring,
  storage: FederationStorage,
): AuthorityConfig {
  return {
    entityId: "https://umu.example", crypto: { engine, keyring: keys }, storage,
    metadata: { federation_entity: {
      federation_fetch_endpoint: "https://umu.example/fetch",
      federation_fetch_endpoint_auth_methods: ["private_key_jwt"],
      federation_list_endpoint: "https://umu.example/list",
    } },
  };
}
```

In this topology, LIGO Wiki is enrolled under InCommon, not under the university. For requests from that RP, configure the university's `clientKeyProvider` to return independently trusted client federation keys; the default subordinate-record lookup alone cannot authenticate it.

## What your application owns

Supply shared replay state before using this configuration. Authenticate client keys; do not trust a request's own key declaration. Authenticated requests use the endpoint's required POST/form composition and audience. Use the shared `authentication` option on the endpoint clients. There is no automatic anonymous retry after invalid credentials. TLS termination and any transport-level identity belong to the host.

## Register another method

Authority uses `endpointAuthentication.methods`; Leaf issuer hosting uses `trustMarkIssuer.authentication.extensions.methods`; Collection uses `authentication.extensions.methods`. Register credential parameter/header names and an `authenticate` callback returning `Result<{ entityId }>`. Advertise only implemented methods in endpoint metadata. The shared verifier contains callback failures, rejects ambiguous credentials, and prevents anonymous fallback after credentials are supplied.

Client `authentication` accepts `private_key_jwt` with a signer and explicit responder audience, or a custom `prepare` callback returning credential headers/parameters. Trust Mark retrieval, status, listing, and historical-key clients share this layer. Authenticated calls use form POST and reject redirects. Host-supplied transport evidence must come from verified infrastructure; a caller's identity header is not authentication.

Additional request parameters cannot replace protocol selectors or credentials. Unknown endpoint extensions remain ignored. A custom verifier is responsible for its method's cryptographic, audience, freshness, and replay checks.

## Test both sides of authentication

Configure the server's supported methods and the client's selected method separately. For a protected university endpoint, test an accepted request, a missing credential, a wrong audience, and a repeated assertion. An application login cookie does not implement federation endpoint authentication.

A custom method needs a verifier on the host and matching request construction on the caller. Declare its parameter names so query/body and selector checks can distinguish credentials from ordinary selectors. Keep private keys and proofs out of logs. A failed authentication callback must prevent the endpoint operation, even if the host logger is unavailable.

## Configure authenticated endpoint requests

Pass `authentication` in the client options for Fetch, Listing, Extended Listing, Resolve, Entity Collection, or Subordinate Events. The client sends `private_key_jwt` or your configured authentication method in a form POST. Without authentication, these clients use GET. Collection also accepts an explicit `method: "POST"` for anonymous requests.

<!-- oidfed-example -->
```ts
import type { CryptoEngine, KeyringEntry } from "@oidfed/crypto";
import { entityId, fetchSubordinateStatement } from "@oidfed/core";

export async function fetchUmeaOpStatement(engine: CryptoEngine, signer: KeyringEntry) {
  return fetchSubordinateStatement(
    "https://directory.umu.example/fetch?tenant=academic",
    entityId("https://op.umu.example"),
    {
      engine,
      issuer: entityId("https://umu.example"),
      authentication: {
        method: "private_key_jwt",
        clientId: "https://wiki.ligo.example",
        audience: "https://umu.example",
        signer,
      },
    },
  );
}
```

The assertion audience is the responder's Entity Identifier, which can differ from its endpoint origin. Keep `authentication.audience` as the audience input; no separate responder parameter is needed. Fetch and Events cross-check it against their existing issuer input when available. Collection traversal also checks the authority identity before requesting its Listing endpoint, and `fetchAndAttachTrustMark()` checks the verified issuer before requesting its Trust Mark endpoint. A mismatch stops the request before credentials are prepared or signed. Standalone Listing, Resolve, Collection, and Extended Listing clients use the audience you supply; a requested Trust Anchor is not necessarily the resolver or collection provider. The receiver checks that the assertion targets its own Entity Identifier. Setting this value does not by itself establish ownership of the endpoint. Collection and Events still accept a caller-created `clientAssertion`; its audience and signature remain the caller's responsibility and are checked by the receiving endpoint. Supplying both `clientAssertion` and `authentication` returns an error.

If you pass a prebuilt `clientAssertion` with an explicit Federation allowlist or artifact policy, the client checks its header algorithm before sending it. A standalone call without either policy forwards the assertion as supplied. The receiving endpoint still verifies the signature and claims.

For a standalone client, keep the endpoint and its authentication in one application configuration. **LIGO Wiki** might have this entry for **eduGAIN**, whose directory lives on another origin:

<!-- oidfed-example -->
```ts
import type { CryptoEngine, KeyringEntry } from "@oidfed/crypto";
import { fetchListSubordinates, type EndpointClientAuthentication } from "@oidfed/core";

export async function listCampusProviders(engine: CryptoEngine, signer: KeyringEntry) {
  // Use trusted application configuration or validated federation metadata.
  const campus = {
    endpoint: "https://directory.edugain.example/list",
    authentication: {
      method: "private_key_jwt",
      clientId: "https://wiki.ligo.example",
      audience: "https://umu.example",
      signer,
    } satisfies EndpointClientAuthentication,
  };

  return fetchListSubordinates(
    campus.endpoint,
    { entityType: "openid_provider" },
    { engine, authentication: campus.authentication },
  ); // Result: the host handles success or failure as usual.
}
```

Here the host establishes the endpoint/identity pairing. The client signs the configured audience, and the receiving endpoint checks it against its own Entity Identifier. Supplying that audience does not independently verify the pairing. Standalone Trust Mark retrieval, Resolve, Extended Listing, and Collection follow the same rule. The client does not retry anonymously when signing, credential preparation, or endpoint authentication fails.

For requests that visit several authorities, use `getEndpointAuthentication` instead of static `authentication`. The callback receives `{ endpoint, responder?, signal? }` and may return credentials synchronously or asynchronously. Returning `undefined` selects anonymous access; throwing or rejecting stops that request. It cannot be combined with `authentication` or a prebuilt `clientAssertion`.

`responder` is supplied when the calling operation knows the Entity Identifier, including Collection traversal, Fetch, Events with an issuer input, and evidence-aware Trust Mark operations. Standalone clients without that context leave it undefined. The library never derives it from the endpoint origin or a requested Trust Anchor. Selected credentials go through the same audience check and POST composition as static credentials, before signing or preparing them.

Use your own configured endpoint and entity allowlist when selecting credentials. The context identifies the request being made; it does not establish trust in an endpoint discovered through a remote graph. Check both values before releasing credentials. See the [Collection traversal example](14.2.collection-operations.md#credentials-for-each-authority).

The callback runs when a federation endpoint request is prepared. Entity Configuration discovery remains anonymous GET and never calls it; cached responses and requests shared within an operation can avoid a new call. Cancelling `signal` stops waiting for a pending callback. Callback errors become a failed `Result` without exposing their text or retrying anonymously. The exported `EndpointAuthenticationProvider` and `EndpointAuthenticationContext` types describe this contract.

Put operation parameters in the form body of every federation POST. For example, an authenticated Fetch to `/fetch?version=1` carries `sub` and the client assertion in the form. The host still uses `version=1` to match the route. A query-only `sub` returns `400 invalid_request` before assertion verification. The same form rules apply to anonymous POSTs on Trust Mark Status and Entity Collection. Anonymous GET requests continue to use the query for operation parameters.

The client keeps the advertised query and includes fixed standard selectors for the current operation in its POST form. For a fixed custom selector such as `campus=north`, pass `additionalParameters: { campus: "north" }` so the client includes it in the form. Membership filters such as `entity_type` allow the same values in a different order or with duplicates. The client uses the advertised sequence, and the host uses the URL's sequence after checking that the form contains the same values. Scalar and custom parameters require the same values in the same order. A conflict fails before the client sends a request.

Put client credential parameters, including `client_id` and `client_secret` when applicable, in the form. The host rejects them in the URL and removes credentials before forwarding the operation. A `private_key_jwt` assertion authenticates the caller to the receiving Entity Identifier. The form parameters are outside the signed assertion.

Federation endpoint clients reject redirects and require HTTP `200`. Generic `performFetch()` retains its configurable transport behavior. EC discovery stays an unauthenticated GET and also requires `200`. A missing EC or Subordinate Statement reported with HTTP `404` returns `not_found`.

These request rules follow [Federation §§8.1–8.9](https://openid.net/specs/openid-federation-1_0.html#section-8) and [Entity Collection §3.3.1](https://openid.net/specs/openid-federation-entity-collection-1_0-01.html#section-3.3.1). Fetching an artifact still does not establish trust in it; use the corresponding verification API.

Custom hosts should match routes and read routing values before calling `createEndpointAuthenticatedHandler()`. The wrapper forwards the validated POST form to the operation handler, using a synthesized query for GET-native handlers. URL routing values stay outside that forwarded input. Pass the route's fixed query in `route.fixedQuery` to check any repeated routing values that also arrive in the form.

Set `config.operationParameterNames` to identify selectors understood by a custom handler. A listed selector requires a matching form value when it appears in the POST URL. Built-in hosts supply their operation-specific standard names and any registered Extended Listing filters or Trust Mark request extensions. Configure `unorderedParameters` for filters whose repeated values express membership. Scalar and other selectors use exact comparison. Core exports `ENDPOINT_OPERATION_PARAMETERS`, `endpointParameterValuesMatch`, and the `*_UNORDERED_PARAMETERS` lists for integrations that share these rules.

## Shared authentication primitives and custom methods

Core supplies the authentication primitives used by the protocol packages. The
calling profile still decides which keys and trust rules apply. For example,
Federation endpoint assertions use **Federation Entity Keys**; PAR assertions use
the RP's **protocol keys**. Both use `createClientAssertion`, with a 60-second
default lifetime and a fresh `jti`. Invalid or non-finite lifetimes fail before
signing. Fractional NumericDates are supported.

`runAsyncOperation` bounds asynchronous host work using `signal` and
`httpTimeoutMs`. A cancelled operation stops waiting, observes late promise
rejections, and cannot report authentication success. Host callbacks should also
honor the signal to stop their own work; cancellation cannot undo a remote side
effect that has already happened.

Custom Federation authentication methods can share a credential carrier, such as
`Authorization`. Set `detect` to identify the method that actually applies. When
present, its result takes precedence over the presence of a registered header or
parameter. A method sharing `client_assertion` must provide a detector. Detection
only selects a verifier: it never authenticates the request. Ambiguous or
unsupported credentials fail, including when anonymous access is allowed.

A verifier may return an `EndpointAuthenticationError` with an
`authenticationResponse`. This carries a controlled OAuth error, HTTP 400 or 401,
and the `OAuth-Client-Attestation-Challenge` or `WWW-Authenticate` headers.
`endpointAuthenticationErrorResponse` validates that response before rendering it;
other headers and unexpected exceptions are not exposed. A
`use_attestation_challenge` response must include its challenge header.

Federation §8.8 still governs Federation endpoints: authentication uses POST,
with endpoint and authentication parameters in the body. The generic Client
Attestation header format is not automatically installed as a Federation
endpoint method. A federation choosing an additional method must define its
integration with those requirements.

## Host authentication and routing rules

Confirm the required authentication method for each endpoint you call or serve. For authenticated Federation endpoint requests, send the credentials and operation parameters in the POST body. In a deployment with replicas, test an allowed request, a caller whose grant excludes the requested subject, and a replay of the same assertion on another replica.

Federation endpoint `private_key_jwt` authentication verifies the remote caller's assertion with keys returned by `clientKeyProvider`. If omitted, the authority uses the caller Entity Identifier to read the subordinate record from `storage.subordinate` and uses that record's `jwks`. Configure a custom provider when caller keys live in an external registry or key service; invalid, missing, or mismatched keys fail closed.

Each hosted federation endpoint uses its own `*_auth_methods` metadata, following [§8.8.1](https://openid.net/specs/openid-federation-1_0.html#section-8.8.1):

| Methods | Access |
|---|---|
| Omitted or `["none"]` | Anonymous requests |
| `["private_key_jwt"]` | Authenticated form POST required |
| `["none", "private_key_jwt"]` | Anonymous requests or authenticated form POST |

The built-in authority rejects empty lists and unsupported method names during construction, including unsupported names mixed with recognized methods. `none` and `private_key_jwt` are built in. Register other methods through `endpointAuthentication.methods` and advertise their names in endpoint metadata. Construction rejects advertised methods without a matching implementation.

A managed endpoint offering `private_key_jwt` needs at least one usable signing algorithm. If you publish `endpoint_auth_signing_alg_values_supported`, every listed algorithm must be supported by the engine and allowed by the host, the client-assertion policy and the endpoint. An omitted field stays absent from the Entity Configuration. At request time the endpoint rejects a disallowed algorithm before looking up the caller's keys.

### Authorize individual requests

A valid assertion authenticates the caller. The receiver may still deny Fetch access to a particular subordinate. Set `authorizeEndpointRequest` in the host’s options and compare `endpoint === "fetch"`, `caller`, and `parameters.sub` against your application’s grants. The hook runs after credentials and replay checks and before the endpoint reads the requested resource. It also runs for anonymous requests where the endpoint allows them. In that case `caller` is `undefined`.

The input includes the receiving Entity Identifier, the operation name, read-only parameter arrays, and an abort signal. Credentials and request headers are kept outside the input. Return `true` to allow the request or `false` for a generic `401 invalid_client`. An error or timeout returns a generic server error. When both host and service options specify a hook, both must allow the request. The hook applies to managed Federation endpoints. Entity Configuration discovery and application-managed routes have their own routing and access rules.

When the host supplies a logger, oidfed records the operation and failure category for policy exceptions, invalid results, and timeouts. Trusted in-process Resolve calls with per-call options bypass the HTTP authorization hook and cannot populate the serving assessment cache.

Most anonymous federation endpoints use GET. Trust Mark Status uses form POST with `trust_mark` whether authentication is enabled or not, as defined in [§8.4.1](https://openid.net/specs/openid-federation-1_0.html#section-8.4.1). Under optional authentication, omitting both credential fields allows anonymous access. Supplied empty, partial, invalid, or replayed assertions are rejected. Requests containing assertions must use POST. Form reads are bounded before dispatch.

Authority endpoints using this middleware require `storage.replay` when `private_key_jwt` is configured. Assertions must include `exp` and a non-empty `jti`; `iat` is optional. After signature and claim validation, the authority atomically claims the assertion before dispatch. Reuse across endpoints sharing that replay store is rejected, and replay-storage failures prevent dispatch. [Collection authentication](14.2.collection-operations.md#authentication-and-http-clients) uses the core service; it accepts a configured replay store or falls back to memory. Production instances must share replay state.

Entity Configuration discovery uses unauthenticated GET independently of these settings, following [§9.1](https://openid.net/specs/openid-federation-1_0.html#section-9.1). Federation defines no discovery auth-method parameter or client-assertion flow for it. The specification does not explicitly prohibit profile-specific network or TLS access controls; deployments using them need matching client transport support.

Authorities remove one trailing `/` from their own configured `entityId` at construction. The resulting published identifier is used consistently by the public `entityId` property, composed roles, Entity Configuration claims, and hosted services. Remote identifiers and authority hints are kept unchanged.

Discovery URL construction is a separate step: remove one trailing `/` from the published identifier, then append `/.well-known/openid-federation`, as §9 specifies. For example, configuring `https://ta.example.org/tenant///` publishes the identifier `https://ta.example.org/tenant//`, whose discovery URL is `https://ta.example.org/tenant//.well-known/openid-federation`. Use the host's published `entityId` when configuring other participants. Port numbers and encoded path components are preserved.

Role routes cannot replace Entity Configuration discovery, another role's route, or a registered federation endpoint. Construction fails with the conflicting path. Because role routes dispatch by pathname, a role also conflicts with an endpoint on that pathname when the endpoint has fixed query selectors. Choose a separate path for the role's handler.

Federation endpoint HTTP routes are derived from the paths advertised in `metadata.federation_entity`, not from fixed defaults. For example, advertising `federation_fetch_endpoint: "https://ta.example.org/custom/fetch"` mounts fetch handling at `/custom/fetch`. Optional endpoints are mounted only when their corresponding endpoint URL is advertised. Endpoint URLs must use HTTPS and contain no fragment. Federation endpoints may share a pathname when their fixed query selectors are disjoint. Construction rejects overlapping routes; role routes match the whole pathname and therefore need a separate path.
