# 9. Updates, rollover, and revocation

**Umeå University OP**’s metadata and keys change while **eduGAIN** continues serving registrations. Operators coordinate publication, propagation, and switching so peers can follow those changes.

Update registrations through the Authority lifecycle methods. Reassess peer trust through the host or role. For key rollover, retain and operate on the provider injected into that host, then publish the resulting configuration; a Leaf needs an explicit refresh for immediate publication.

## Maintain trust as the federation changes

A working enrollment is a starting point. Umeå may rotate keys, change protocol endpoints, or leave eduGAIN. Authorities update their records and future statements; consumers discover those changes when they refresh evidence or react to another federation-defined signal.

For key rollover, publish the replacement before switching the signer, allow the chosen propagation period, and retain the old public key for the required overlap. Consumers can compare the anchor's published keys with an independently authenticated source. Persistent disagreement needs the operator's remediation policy.

For withdrawal, understand what remains in circulation. A removed record cannot delete cached signed statements, registrations, or user sessions. Keep each application's evidence deadlines and reevaluation behavior explicit. Federation leaves the broader revocation process to the trust framework, so document any stronger deployment mechanism alongside ordinary expiration and refresh.

## OpenID Federation

### Rollover, freshness, and revocation

Use oidfed's [federation key contracts](9.4.federation-keys.md#keep-key-history-factual) to publish keys, switch signers, retire keys, and retrieve historical keys. For a Trust Anchor, the application drives the four stages in [§11.2](https://openid.net/specs/openid-federation-1_0.html#section-11.2):

1. Publish the new public keys.
2. Keep signing with the old keys while participants obtain the new ones.
3. Switch to signing with the new keys.
4. Remove the old keys after a suitable overlap.

More generally, [§11.1](https://openid.net/specs/openid-federation-1_0.html#section-11.1) uses Entity Configuration expiry to control when participants retrieve updated federation keys.

[§11.2](https://openid.net/specs/openid-federation-1_0.html#section-11.2) leaves overlap timing to the Trust Anchor's security profile and risk assessment. The operator chooses Entity Configuration lifetimes, how long to wait before switching, and how long to retain the old keys afterward. The host schedules retirement explicitly; see [key rollover](9.5.key-rollover.md). The specification prescribes no such duration, and this setting does not control the pre-switch wait.

A Leaf [caches its Entity Configuration](2.1.entity-configuration.md#how-does-the-entity-configuration-caching-work). Call `refreshEntityConfiguration()` when changed keys or a new signer need to be published before the cached JWT expires. As deployment guidance, account for proxy caches when choosing publication timing.

[§11](https://openid.net/specs/openid-federation-1_0.html#section-11) requires participants to support refreshing expired Trust Chains. A chain expires with its earliest-expiring statement under [§10.4](https://openid.net/specs/openid-federation-1_0.html#section-10.4), and [§10.2](https://openid.net/specs/openid-federation-1_0.html#section-10.2) requires checking statement times. Core checks these times during [chain validation](3.1.chain-validation.md#candidate-discovery-and-chain-checks). Your application must reevaluate trust before continuing to rely on expired evidence. oidfed does not schedule reevaluation of trust decisions retained by applications. Use `refreshTrustChain()` for replacement evidence; `forceRefresh: true` bypasses pre-existing statement-cache entries when an earlier change check is needed. See [refresh behavior and clocks](9.3.chain-refresh.md#refresh-behavior-and-cache-bypass).

[§11.4](https://openid.net/specs/openid-federation-1_0.html#section-11.4) defines no federation-wide revocation process; a federation `MAY` define its own. In oidfed, [`revokeKey()`](../../packages/core/src/federation-keys.ts) changes local provider state and historical records. [`revokeSubordinate()`](../../packages/authority/src/subordinate-lifecycle.ts) removes the current registration. Neither invalidates statements cached elsewhere, and [§10.2](https://openid.net/specs/openid-federation-1_0.html#section-10.2) permits caching until expiry. A chain refresh can therefore succeed after subordinate removal if it reuses a still-valid cached Subordinate Statement. Subordinate Events can help applications learn about changes when they query the endpoint; it is not a push notification service. Use `revokeSubordinate()` for the administrative removal and its event recording, rather than bypassing that lifecycle through storage directly.

After revoking the last active signing key, explicitly activate a published replacement to restore signing. Arrange trusted distribution of that replacement under your incident-response policy.

For historical verification, `selectHistoricalVerificationKey` rejects all revoked keys by default. Use `allowedRevocationReasons` to explicitly allow non-security reasons for signatures created strictly before revocation and within the key's validity window. [§8.7.3](https://openid.net/specs/openid-federation-1_0.html#section-8.7.3) allows custom reasons; declare additional security reasons through `securityRevocationReasons`. Built-in and configured security reasons always reject the key, even if also allowlisted. Ordinary retirement without revocation remains subject to the key's validity checks.

The operator defines any additional federation revocation process. [Trust Mark Status](https://openid.net/specs/openid-federation-1_0.html#section-8.4) and [historical-key revocation fields](https://openid.net/specs/openid-federation-1_0.html#section-8.7.2) cover their respective objects; they do not define a general participant-revocation protocol.
