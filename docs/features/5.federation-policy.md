# 5. Federation policy

**eduGAIN** sets rules for subordinate metadata and for the paths that participants may use. A superior expresses those rules in the Subordinate Statements it issues. [Federation §6](https://openid.net/specs/openid-federation-1_0.html#section-6).

A `TrustAnchor` or `Intermediate` publishes policies and constraints through its subordinate records. Consumers install custom checks in their host or role options and call the normal trust operation. Those operations invoke the shared core engine; applying policy again afterward is unnecessary.

## Agree on policy before enforcing it

eduGAIN chooses restrictions for a participant or a class of participants and includes them in the appropriate Subordinate Statements. LIGO Wiki resolves the policies along the authenticated path and applies them to the metadata it will use. The same participant can therefore have different usable metadata through different federation paths.

Confirm the participation rules with the federation operator. During Trust Chain validation, oidfed evaluates the metadata policy and constraints in the chain. A receiving application separately applies [endpoint grants](7.5.endpoint-authentication.md#authorize-individual-requests) to decide what a caller may request.

Start with built-in operators and constraints, and test the resulting metadata against representative inputs. When a federation needs a custom rule, define its semantics and deploy the consuming implementation before relying on it. Publishing a new name does not distribute callback code to peers.

Keep an accepting case and a rejected case for each important policy. A policy error should stop the dependent protocol operation, with enough diagnostic context for operators to locate the conflicting statement. The solution is a corrected policy or another valid path, not removing the failed check from the consumer.
