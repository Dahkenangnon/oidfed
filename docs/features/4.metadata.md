# 4. Metadata

[Feature guides](README.md)

**Umeå University OP** advertises its OP capabilities; **Licensing Authority** describes its credential service. Their own publications may be partial because a superior can supply values before the application consumes effective metadata. [Federation §5](https://openid.net/specs/openid-federation-1_0.html#section-5).

Put local protocol metadata on the OIDC or Wallet role attached to the host. Use the role's publication parser for editing drafts and its effective parser for complete metadata. Superior changes go through Authority enrollment methods; consuming role operations apply the resulting policy.

## From an operator draft to effective metadata

Umeå's operator edits the fields Umeå owns. A publication parser checks supplied values while allowing fields a Superior can complete. eduGAIN may contribute metadata in its Subordinate Statement and apply a policy along the path. LIGO Wiki sees the resolved result of those contributions.

Use the effective protocol parser before consuming that result. For example, an OP's publication draft and a complete OP discovery configuration have different completeness requirements. A dashboard can show both views: the editable draft and a read-only preview of the metadata a consumer would accept through a chosen anchor.

Keep the identity binding and key sources visible during review. Metadata extensions remain possible, but a host using an extension needs to understand its meaning. A field surviving parsing is not evidence that the application has implemented the feature it describes.
