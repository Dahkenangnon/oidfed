# 8. Discovery and caching

[Feature guides](README.md)

**LIGO Wiki** begins with **Umeå University OP**’s Entity Identifier, fetches its EC, and searches for usable paths. It can cache evidence and choose among validated chains according to application policy. [Federation §§9–10](https://openid.net/specs/openid-federation-1_0.html#section-9).

Configure anchors, selection, transport, and caching on the host or role, then use its discovery or protocol operation. Core helpers remain useful for diagnostics that need raw candidate chains, rather than one accepted result.

## Explore, validate, then choose

LIGO Wiki obtains Umeå's configuration and follows authority hints to build candidate paths. Its configured anchors decide where those paths can establish trust. An anchor can have Superiors of its own, and discovery can find a path to a higher configured anchor when the topology permits it.

The operation has resource bounds. Shared fetch budgets cover discovery and validation work, and a cancelled caller should stop waiting promptly. Cache hits can reduce transport, but they cannot extend signed validity. Diagnose incomplete discovery separately from an invalid chain.

After validation, apply the operation's protocol checks and path-selection policy. A custom selector expresses LIGO Wiki's preference among eligible candidates. It cannot manufacture a new validated result or turn an incomplete graph search into a complete assessment of every possible path.

## Multiple paths and trusted resolvers

Decide which anchors an operation accepts before choosing a path. A selection strategy ranks eligible chains; it does not expand that trust set. Different paths can produce different metadata, so choose a strategy that suits the federation's policies and recipient requirements. [Federation §17.1](https://openid.net/specs/openid-federation-1_0.html#section-17.1) assigns that topology decision to federation architects.

Size the fetch allowance for discovery and candidate validation together. Core helpers share a default allowance of 50 HTTP client calls across those stages. Custom selection fails if discovery is truncated by a resource limit; a Resolve service returns `temporarily_unavailable` in that case. Adjust limits for the expected topology without removing the bounds that protect the service.

Explicitly authorize each resolver and configure how its keys become trusted. Use local assessment when your application needs its own custom policy or constraint checks, or when its protocol requires chain validation. Delegated assessments report what the trusted resolver asserts, including reported marks; they do not create locally verified mark evidence. Keep both provenance and expiry with any application decision.

A catalog built with Listing or Entity Collection can contain identifiers and informational metadata without establishing application trust. Establish that trust when using the selected entity. A standalone resolver can share the same core Resolve service as Authority hosts without acquiring subordinate-management duties. See [trust establishment options](8.3.chain-selection.md#configure-selection-across-federation-operations).
