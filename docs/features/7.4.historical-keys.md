# 7.4. Retrieve authenticated historical federation keys

**eduGAIN** rotated a signing key after issuing a JWT that a consumer still needs to examine. A historical key response records old public keys and their lifecycle information.

## How to use it

Trust Anchors, Intermediates, and Leaves can serve Historical Keys. Set `federation_historical_keys_endpoint` in the entity's `federation_entity` metadata and supply `crypto.history`. Use `historicalKeysFromKeyring(keyring)` for a rotating keyring, or supply the public records from your own history store. `getHistoricalKeys()` signs the history and `handleRequest()` serves the configured URL. Trust Mark consumers can configure historical lookup on their host or role. [Historical keys](https://openid.net/specs/openid-federation-1_0.html#section-8.7).

```ts
import type { TrustAnchor, Intermediate } from "@oidfed/authority";

export function campusHistory(campus: TrustAnchor | Intermediate) {
  return campus.getHistoricalKeys(); // Signed using the host's current federation signer.
}
export function serveCampus(campus: TrustAnchor | Intermediate) {
  return (request: Request) => campus.handleRequest(request);
}
```

For a Leaf, compose the history source and endpoint with its existing configuration:

<!-- oidfed-example -->
```ts
import type { FederationKeyHistorySource } from "@oidfed/core";
import { Leaf, type LeafConfig } from "@oidfed/leaf";

export function createLeafWithHistory(config: LeafConfig, endpoint: string, history: FederationKeyHistorySource) {
  return Leaf.create({
    ...config,
    crypto: { ...config.crypto, history },
    metadata: {
      ...config.metadata,
      federation_entity: {
        ...config.metadata.federation_entity,
        federation_historical_keys_endpoint: endpoint,
      },
    },
  });
}
```

The Leaf registers its managed route when both the URL and history source are supplied and there is no role route at that path. Keep the managed route's advertised URL and authentication settings fixed across role metadata refreshes. Use fixed query parameters for route selection and send authentication form parameters in the POST body. For `private_key_jwt`, advertise the method and algorithms, supply `historicalKeysAuthentication.getClientFederationJwks`, and configure replay storage. Historical JWKs must satisfy their registered public-key format. [Leaf configuration](../api/leaf/hosts.md#leafconfig)

Omit the URL to sign history in-process. A role that serves the endpoint keeps its route even when `crypto.history` is configured. Configure its authentication in the role handler and reserve `historicalKeysAuthentication` for Leaf's managed route. An application can also serve the endpoint outside Leaf by advertising its URL and omitting the history source. Leaf logs a warning if it has no matching local handler. The application must route requests on the advertised origin, which may differ from the Leaf's Entity Identifier origin. Leave the endpoint off for protocol Leaves whose deployment profile prohibits `federation_entity` metadata. [Swedish profile §2.2](https://www.oidc.se/specifications/swedish-openid-federation-profile-1_0.html#section-2.2)

## Retrieve history for a custom verifier

For a verifier outside an existing host or protocol workflow, core provides the remote client. It verifies the response, not the older artifact you intend to check:

<!-- oidfed-example -->
```ts
import type { CryptoEngine } from "@oidfed/crypto";
import { fetchHistoricalKeys, type JWKSet } from "@oidfed/core";

export function remoteCampusHistory(engine: CryptoEngine, currentTrustedKeys: JWKSet) {
  return fetchHistoricalKeys("https://edugain.example/historical-keys", currentTrustedKeys, {
    engine,
    expectedIssuer: "https://edugain.example",
  });
}
```

Check the `Result` before selecting a key. Standalone selection uses `selectHistoricalVerificationKey()`; the [historical Trust Mark workflow](6.10.trust-mark-historical-keys.md) composes that step automatically.

## What your application owns

Retain accurate activation, expiry, and revocation records in the keyring. Establish trust in the current response signer independently of the historical key being sought. Old-key availability does not extend an artifact's expiry or prove current accreditation. The shared historical-key selector enforces finite signing time, key `iat`/`nbf` lower bounds, exclusive `exp`, and explicit revocation policy. Trust Mark verification can opt into missing-key history lookup or use supplied offline responses; see the [mark workflow](6.10.trust-mark-historical-keys.md).

## Retain enough history for surviving artifacts

When eduGAIN rotates keys, existing signed artifacts may still need verification. Keep the relevant public history and validity information available for the lifetimes your federation supports. Never publish private signing material through the history endpoint.

Consumers establish trust in the history source and validate the signed response before selecting a key. A historical key answers which public key was used during an interval; it does not automatically restore trust in an expired chain or revoked artifact. Coordinate history retention with Trust Mark lifetimes and your offline requirements.
