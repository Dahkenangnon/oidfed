# 9.5. Publish, propagate, and switch federation keys

[Feature guides](README.md) / [9. Updates, rollover, and revocation](9.updates-and-keys.md) · [Example context](9.updates-and-keys.md#example-context)

**eduGAIN** prepares a replacement key while the old key still signs its statements. **Umeå University OP** must have time to obtain the new public key before it encounters a statement signed with it.

## How to use it

Keep the provider you attached to the host and operate on that same instance. Core defines the lifecycle contract; the host exposes the resulting signed publications. Call `publishReplacement()` first, serve and inspect that publication, wait for the operator's propagation interval, then call `switchAfterPropagation()` as a separate administrative step. These functions do not schedule a wait for you. [Federation key rollover](https://openid.net/specs/openid-federation-1_0.html#section-11.1); [Historical keys](https://openid.net/specs/openid-federation-1_0.html#section-8.7).

```ts
import { TrustAnchor, type StorageAdapter } from "@oidfed/authority";
import { createFederationSigningKey, generateSigningKey, type FederationKeyLifecycleProvider } from "@oidfed/core";

export function eduGainRollover(keyProvider: FederationKeyLifecycleProvider, storage: StorageAdapter) {
  const eduGain = new TrustAnchor({
    entityId: "https://edugain.example", keyProvider, storage,
    metadata: { federation_entity: {
      federation_fetch_endpoint: "https://edugain.example/fetch",
      federation_list_endpoint: "https://edugain.example/list",
      federation_historical_keys_endpoint: "https://edugain.example/history",
    } },
  });
  return {
    eduGain,
    async publishReplacement() {
      const { privateKey } = await generateSigningKey("ES256");
      const replacement = createFederationSigningKey(privateKey);
      await keyProvider.publishKey(replacement);
      return { kid: replacement.signer.kid, configuration: await eduGain.getEntityConfiguration() };
    },
    async switchAfterPropagation(kid: string) {
      await keyProvider.switchActiveKey(kid, { retirePreviousAfterMs: 7 * 24 * 60 * 60 * 1000 });
      return eduGain.getEntityConfiguration();
    },
  };
}
```

## What your application owns

Choose overlap from statement lifetimes and cache behavior; seven days here is an example, not a universal protocol deadline. Arrange superior key-attestation updates too. Refresh cached publications at each stage. Authority EC requests read the current provider state; a Leaf retains its cached EC until expiry or `refreshEntityConfiguration()`. Updating the provider alone does not replace that cached Leaf publication. An emergency `revokeKey(kid, reason)` changes local state but cannot erase remote cached evidence. Retain historical public keys and apply a separate compromise-response policy. Most JWT times use seconds; `retirePreviousAfterMs` explicitly uses milliseconds.

## Observe each rollover stage

First publish the replacement public key while the old key still signs. Retrieve a new Entity Configuration through the external endpoint and confirm both keys are visible. Allow the propagation interval chosen by the operator before switching the active signer.

After switching, verify a newly issued configuration with the replacement key and confirm existing evidence remains usable during the overlap. Retire the old key only after the chosen interval and retain the required public history. For a Leaf, refresh its cached Entity Configuration when an immediate publication is needed. The wait and overlap periods are deployment policy, not proof that every peer has refreshed.

## Publication, propagation, and retirement details

Applications drive rollover through the injected `FederationKeyLifecycleProvider`. [Federation §11.2](https://openid.net/specs/openid-federation-1_0.html#section-11.2) describes four stages: publish the new keys, continue signing with the old keys while participants refresh, switch signers, then remove the old keys after a suitable overlap.

First, publish the next key:

The `publishReplacement()` operation above returns the replacement identifier and a fresh configuration. Confirm that the new key is published while the old key still signs.

The authority's next Entity Configuration contains the new public key and is still signed by the current signer. Authority configuration requests read the provider's current state. If a proxy caches those responses, account for its cache lifetime when choosing the propagation interval.

After the federation's publication and propagation interval, run the switch as a separate administrative step:

Call the returned `switchAfterPropagation(kid)` only after the chosen propagation interval. It changes the active signer and obtains a configuration signed with that key.

The memory provider now signs with the new key and keeps the previous signer's public key available until the retirement deadline. Subsequent key-set reads exclude that old key at the deadline; its historical record remains. No background deletion timer runs. Other active keys, if supplied during initialization, are unaffected by this switch.

With the memory provider, the Historical Keys endpoint publishes retired and revoked keys. Before any such event, it returns a signed response with `keys: []`. Each key retains its recorded `exp` across requests; the response's `iat` identifies when that response was signed. The [core key lifecycle documentation](9.4.federation-keys.md#providers-publication-checks-and-key-history) explains retirement and revocation timestamps. The endpoint signs the history supplied by a custom provider, whose records must describe actual key lifetimes under [§8.7.2](https://openid.net/specs/openid-federation-1_0.html#section-8.7.2).

The propagation interval before switching and the retirement interval after switching serve different stages. The application chooses when to switch; `retirePreviousAfterMs` controls only the post-switch overlap. Seven days is the memory provider's default, not a duration prescribed by the specification. Choose both intervals and Entity Configuration expiry according to the federation's security profile. A Leaf using the same provider must refresh its cached configuration after key-set changes; see [Leaf configuration caching](2.1.entity-configuration.md#how-does-the-entity-configuration-caching-work).

Production key providers must preserve lifecycle state across restarts and coordinate serving processes. The in-memory provider does not persist or distribute changes.

`revokeKey(kid, reason)` applies the provider's local revocation policy. It excludes the key from current publication and signer selection and retains historical revocation information under [§8.7.2](https://openid.net/specs/openid-federation-1_0.html#section-8.7.2). It does not invalidate statements already held by other participants. [§11.4](https://openid.net/specs/openid-federation-1_0.html#section-11.4) leaves the federation-wide revocation process to the trust framework.

## Refresh a Leaf after its provider changes

A Leaf can use a lifecycle-capable provider even though its required interface is smaller. Retain that provider in the same way, perform the lifecycle operation, and refresh its cached configuration:

```ts
import type { Leaf } from "@oidfed/leaf";

export function publishLeafKeyChanges(leaf: Leaf) {
  return leaf.refreshEntityConfiguration();
}
```

For production, the administrative key service supplies durable keys. The generated key above is a local example; each provider transition and publication belongs to the same entity identity.
