# 7. Federation endpoints

[Feature guides](README.md)

Participants retrieve statements, list subordinates, and ask resolvers for evidence. The authority hosts these endpoints; clients authenticate the returned evidence and apply their own trust configuration. [Federation §8](https://openid.net/specs/openid-federation-1_0.html#section-8).

Configure the served endpoints on `TrustAnchor`, `Intermediate`, or a supported `Leaf` integration, and pass requests to `handleRequest()`. Local administrative methods use the same host services. Remote callers use a role workflow or, for a direct endpoint query, the matching core client.

## Choose the endpoint for the question

Use Fetch for an authority's statement about a subordinate, Listing to enumerate participants, and Resolve to obtain an assessment or chain through a resolver. Historical Keys supplies signed public-key history. Trust Mark status, listing, and retrieval have their own questions and are covered with the accreditation lifecycle.

First obtain the endpoint location from trusted configuration or validated metadata. Then apply that endpoint's authentication policy and transport limits. An endpoint on a different origin can still belong to the same federation entity; the authentication audience is the responder's Entity Identifier, not a URL guessed from that origin.

Treat the response according to its contract. A listing supplies discovery input, a signed history response supplies historical evidence, and a Resolve result has the trust boundary selected by the caller. HTTP success alone does not make their contents interchangeable with a locally validated chain.
