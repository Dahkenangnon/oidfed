# 11.2. Consume one-time JWT identifiers atomically

[Feature guides](README.md) / [11. Operating a federation application](11.operations.md) · [Example context](11.operations.md#example-context)

A wallet proof accepted at **Car Rental Company** must not work a second time, even when the repeated request reaches another replica. The same problem applies to client assertions at **eduGAIN**'s protected endpoints.

## How to use it

Supply the replay store to the role or endpoint that consumes the proof. Here **Umeå University OP**'s initialized OP role claims the Request Object identifier while processing automatic registration. Replaying an otherwise valid Request Object fails through that operation. Core supplies the shared `ReplayStore` contract and development adapter; the application does not manually consume the same identifier again. [Attestation proof processing](https://www.ietf.org/archive/id/draft-ietf-oauth-attestation-based-client-auth-07.html#section-5).

```ts
import { Leaf } from "@oidfed/leaf";
import { OidcProviderRole, type OidcProviderRoleConfig } from "@oidfed/oidc";
import { MemoryReplayStore, type FederationKeyProvider, type ReplayStore, type TrustAnchorSet } from "@oidfed/core";

export function umeaOpWithReplayProtection(
  keyProvider: FederationKeyProvider, trustAnchors: TrustAnchorSet, opMetadata: Record<string, unknown>,
  onRegistration: NonNullable<OidcProviderRoleConfig["onRegistration"]>,
  replayStore: ReplayStore = new MemoryReplayStore(), // Development default only.
) {
  const op = new OidcProviderRole({
    replayStore, onRegistration,
    metadata: { ...opMetadata, client_registration_types_supported: ["automatic", "explicit"] },
  });
  const umeaOp = new Leaf({
    entityId: "https://op.umu.example", authorityHints: ["https://umu.example"],
    keyProvider, trustAnchors, metadata: { federation_entity: {} }, roles: [op],
  });
  return {
    umeaOp, op,
    acceptRequest: (jwt: string) => op.processAutomaticRegistration(jwt),
  };
}
```

Pass Umeå's actual OP capabilities and endpoints as `opMetadata`; the example focuses on the replay-store wiring. Use a shared durable `ReplayStore` in place of the default memory store when several processes accept requests. Federation endpoint authentication uses the Authority's `storage.replay`, while Wallet proof APIs accept a replay store in their authentication options. These are separate configuration locations, even if a deployment implements them over the same backend.

## What your application owns

Use durable, shared atomic storage for a replicated receiver. Retain identifiers through the accepted expiry and skew window, and fail closed when the store is unavailable. Keep namespaces isolated. A plain get-then-set sequence is not atomic. Supply a store independently to each endpoint or role that requires one; attaching a role does not connect every store automatically.

## Share replay decisions across accepting workers

If Umeå accepts the same proof on two workers, an in-memory replay store on each worker cannot make the decision atomic across the deployment. Use shared state with an atomic consume operation for the acceptance boundary that must reject a repeated identifier.

Keep the stored replay lifetime aligned with the proof's acceptance window, including the configured clock policy. A failed write must not mean the proof was accepted without replay protection. Exercise two concurrent uses in a test and confirm that only the permitted first use succeeds.

## How do OPs prevent Request Object replay attacks?

A Federation automatic-registration Request Object needs a `jti` and `exp`. OP-side processing checks expiry and claims the `(issuer, audience, jti)` tuple through the configured `ReplayStore`. The claim is retained until `exp + clockSkewSeconds`, covering the full acceptance window required by [Federation §12.1.1.1](https://openid.net/specs/openid-federation-1_0.html#section-12.1.1.1). Use a shared atomic implementation across instances; the OP role requires this store for automatic registration.

## Assertion verification and replay storage

`verifyClientAssertion()` requires `exp` and a non-empty `jti`; `iat` is optional. It checks the signature, issuer/subject equality, exact audience, expiry, and any supplied issuance time. Pass `replayStore` to atomically claim a verified assertion. Expiry is checked again after replay storage completes. Without it, the function verifies the JWT without recording its use. Authentication handlers must provide replay storage. These claims follow [OIDC Core §9](https://openid.net/specs/openid-connect-core-1_0.html#ClientAuthentication), referenced by [Federation §8.8](https://openid.net/specs/openid-federation-1_0.html#section-8.8).

A `ReplayStore` claims an `(issuer, audience, jti)` tuple until expiry. Claims must be atomic across the processes serving one tenant. The in-memory implementation is for development and tests.

`MemoryReplayStore` retains the full SHA-256 digest of the JSON tuple `[issuer, audience, jti]`. Stored keys have a fixed size even when valid identifiers are long. Claims that expire during hashing are rejected. The default capacity is 10,000 unexpired entries. At capacity, `useJti()` rejects with `ReplayStoreCapacityError` and preserves every live entry. A replay or expired claim returns `false`; malformed claims reject with `TypeError`. A storage failure must stop acceptance of the assertion or proof.

```ts
import { MemoryReplayStore, ReplayStoreCapacityError } from "@oidfed/core";
import type { JtiReplayClaim } from "@oidfed/core";

const store = new MemoryReplayStore({ maxEntries: 1000 });

// Call after verifying the assertion's signature and claims.
export async function recordVerifiedAssertion(claim: JtiReplayClaim): Promise<Response> {
  try {
    const isNew = await store.useJti(claim);
    return isNew
      ? new Response(null, { status: 204 })
      : new Response("Assertion already used or expired", { status: 401 });
  } catch (error) {
    if (error instanceof ReplayStoreCapacityError) {
      return new Response("Replay protection temporarily unavailable", { status: 503 });
    }
    throw error; // Let the host's error handler reject other storage failures.
  }
}
```

Here, `204` reports a successful replay-store claim only. The host continues its request processing only after that result; `401`, `503`, and rejected operations stop acceptance. Federation authentication helpers already contain replay-store failures and return an authentication error `Result`.
