# 11.6. Build durable storage adapters

[Feature guides](README.md) · [Example context](11.operations.md#example-context)

`@oidfed/authority` accepts one `StorageAdapter` for its authority-owned state: subordinate records and configured Trust Mark, event, collection, replay, and cache capabilities. OIDC registrations and sessions, wallet protocol state, and role-specific replay stores use separate integration points. The bundled `MemoryStorageAdapter` is for development and tests only; production deployments need shared, durable implementations.

Federation key custody, public-key publication, and rollover use the separate `RotatingKeyring` contract.

See [operator and application responsibilities](11.operations.md) for ownership boundaries and specification requirements.

```ts
import type { TrustAnchor, Intermediate } from "@oidfed/authority";
import { entityId } from "@oidfed/core";

export function withdrawWithEvent(campus: TrustAnchor | Intermediate) {
  return campus.revokeSubordinate(entityId("https://op.umu.example"), {
    eventDescription: "Participation agreement ended",
  });
}
```

## Adapter shape

The [`StorageAdapter` reference](../api/authority/storage.md#storageadapter) lists the current methods, parameters, and return types. Implement that exported contract rather than maintaining a local copy.

Each adapter represents one logical authority namespace. Processes serving the same authority must share that state; distinct authority identifiers need separate namespaces. Subordinate operations do not receive an authority identifier on each call, so bind them to the configured namespace. Trust Mark candidate queries and issuer-scoped revocation also carry an issuer selector; preserve it when the service supplies it.

A production adapter should bind the nested repositories to one ORM/database client. `transaction()` must pass transaction-bound repositories, commit atomically, roll back on failure, and provide serializable isolation. The callback may be retried after serialization conflicts, so it must contain storage operations only.

Replay and cache are excluded from `StorageTransaction`: replay claiming is independently atomic, while cache data is non-authoritative.

Application code normally calls the host's `revokeSubordinate()` as above. The host performs its lifecycle work through the adapter transaction. Adapter implementers can test the repository-level atomicity separately; those tests do not replace the host's publication and lifecycle checks.

```ts
import { type StorageAdapter } from "@oidfed/authority";
import { type EntityId } from "@oidfed/core";

export async function exerciseAdapterTransaction(storage: StorageAdapter, issuer: EntityId, subject: EntityId) {
  await storage.transaction(async (tx) => {
    if (!tx.subordinateEvents) throw new Error("Event storage is required");
    await tx.subordinates.remove(subject);
    await tx.subordinateEvents.append(issuer, subject, [
      { iat: Math.floor(Date.now() / 1000), event: "revocation" },
    ]);
  });
}
```

## Subordinates

`SubordinateStorage` provides `get`, `list`, `add`, `update`, and `remove`.

- `entityId` is immutable; adapters preserve `createdAt` and manage `updatedAt` on updates. All three fields are excluded from `SubordinateRecordUpdate`. Direct `add()` calls supply a complete record, including timestamps; `registerSubordinate()` supplies those timestamps for you.
- Duplicate `add` and update/remove of unknown entities throw.
- Inputs to `add`, `update`, and Trust Mark `issue` are captured before asynchronous work. Later caller mutations must not alter a queued write. Validate the captured input; for updates, merge with the current stored record inside the transaction and validate that result.
- Returned values are detached; mutation does not persist data.
- Listing is lexicographic by `entityId` with an inclusive first-unreturned cursor.
- A page may contain no matching records and still provide `nextCursor`. Continue scanning from that position; absence of `nextCursor` means exhaustion. Continuations must advance beyond the incoming cursor and all records in the returned page. Calls without pagination options return all matches.
- Trust-mark filters include `validAt` and are evaluated by the adapter, allowing one database query instead of endpoint-level N+1 checks.
- `createdAt` and `updatedAt` are NumericDates.
- Extended Listing custom request filters run in the handler after these standard storage filters. Keep returning ordered pages and valid continuations; do not apply the custom predicates in the adapter. The handler counts matching records toward its response limit and preserves a continuation when its scan budget is exhausted. No adapter migration is needed.

Suggested relational columns: `authority_id TEXT`, `entity_id TEXT`, `PRIMARY KEY (authority_id, entity_id)`, `jwks JSONB`, `metadata JSONB`, `metadata_policy JSONB`, `constraints JSONB`, `entity_types TEXT[]`, `is_intermediate BOOLEAN`, `source_endpoint TEXT`, `created_at DOUBLE PRECISION`, `updated_at DOUBLE PRECISION`.

## Trust marks

`isStoredTrustMarkEligible(record, validAt)` shares the memory stores' active-state and mark/delegation time checks with adapter authors. Call it before selecting the newest record. It assumes ingestion already verified the JWT, its issuer, and the record's matching fields; it is not a signature or trust validator. See the [storage contract](11.6.storage-adapters.md#trust-marks).

Trust-mark storage is optional. If an authority advertises a trust-mark endpoint, the capability is required at startup.

The [`TrustMarkStorage` reference](../api/core/marks.md#trustmarkstorage) lists the current methods, parameters, and return types. Implement that exported contract rather than maintaining a local copy.

- A record is currently eligible when it is active, has a finite `issuedAt <= validAt`, and either has no expiry or has `expiresAt > validAt`. An embedded delegation must also decode successfully, have finite `iat <= validAt`, and have no `exp` or `exp > validAt`. The shared core predicate `isStoredTrustMarkEligible(record, validAt)` implements these time and active-state checks for records verified at ingestion. Apply these checks before selecting the newest mark so a future-dated replacement does not hide a currently valid mark. This implements [Federation §7.3](https://openid.net/specs/openid-federation-1_0.html#section-7.3)'s time checks using the authority's exact clock, with same-second issuance accepted. Consumer verification has its own clock-skew tolerance.
- Stored type, subject, issuance time, and optional expiration must match the signed JWT. Ingestion establishes signature validity and issuer trust; decoding a stored JWT only checks its contents. Extended Listing checks the reference's type and subject against the JWT before publishing it, following [Federation §3.1.2](https://openid.net/specs/openid-federation-1_0.html#section-3.1.2).
- Every issued JWT is preserved. Reissuance must not overwrite historical records.
- `getByJwt` identifies the exact issued token used by status responses.
- Issuing the same JWT is idempotent.
- Revocation records `active: false` and `revokedAt` without deleting the JWT.
- Listing is deterministic by subject. Its inclusive cursor identifies the first unreturned subject and must support complete traversal.

Suggested relational columns: `authority_id TEXT`, `jwt_hash BYTEA`, `PRIMARY KEY (authority_id, jwt_hash)`, `jwt TEXT NOT NULL`, `trust_mark_type TEXT`, `subject TEXT`, `issued_at DOUBLE PRECISION`, `expires_at DOUBLE PRECISION`, `active BOOLEAN`, `revoked_at DOUBLE PRECISION`. Prefix trust-mark indexes with `authority_id`, for example `(authority_id, trust_mark_type, subject, active, expires_at)` and `(authority_id, subject, active, expires_at)`.

Hashing the JWT for indexing is acceptable, but `getByJwt` must compare the exact token and handle hash collisions safely.

### Adapter migration for managed issuance

`listCandidates()` is required. Return every matching record, including revoked and expired records, from one consistent view. Return detached copies. Do not deduplicate subjects or discard older candidates: the shared issuer service must check signatures, profile rules, and delegation dates before selecting a current record. Eligible records sort by descending `issuedAt`, then descending JWT string for ties. `getByJwt()` must still find revoked records for exact-token Status queries.

An Authority adapter's `readSnapshot()` must expose `trustMarks.listCandidates` and `trustMarks.getByJwt`. A standalone or Leaf issuer uses `TrustMarkStore` with `trustMarks`, `transaction(callback)`, and `readSnapshot(callback)`. The memory adapters implement both contracts.

Reuse selection and insertion happen in serializable transactions. The service signs outside the transaction, then rechecks candidates and policy generation before insertion. An adapter shared across processes must serialize competing issuances itself; an in-process queue provides no distributed guarantee. Revocation's optional issuer selector must restrict updates when supplied. The managed service always supplies it so one issuer cannot revoke another issuer's records in a shared store.

Keep every issued JWT, including superseded and revoked records. Exact duplicate insertion must not reactivate a revoked record. Failed reads or incomplete candidate enumeration must fail the operation rather than produce a successful partial listing.

## Replay protection

The [`ReplayStore` reference](../api/core/contracts.md#replaystore) lists the current methods, parameters, and return types. Implement that exported contract rather than maintaining a local copy.

`useJti` returns `true` only for a newly accepted tuple and `false` for replay or an expired claim. The operation must be atomic across every process serving the same receiver, including Federation Entities and OPs. Authority endpoint authentication middleware requires `storage.replay` when `private_key_jwt` is configured; anonymous endpoints do not. The shared Collection service accepts its own replay store, uses authority replay storage when available, or falls back to memory. Production instances must share the configured replay state. Replay records remain live through the accepted clock-skew window.

Use a unique database or Redis key derived from the complete `(issuer, audience, jti)` tuple. A full SHA-256 digest of its JSON array encoding bounds key size while preserving tuple separation; `MemoryReplayStore` uses this representation. Store the digest and expiry atomically, retaining every unexpired claim. Redis implementations should use one atomic `SET key 1 NX EX ttl` operation. `MemoryReplayStore` defaults to 10,000 unexpired entries and rejects with `ReplayStoreCapacityError` when full; it preserves existing live entries. A direct caller must handle that rejection as unavailable replay protection, separately from the `false` result for replay or expiry. Backend failures must fail closed; never evict unexpired claims to make capacity.

## Cache

`storage.cache` implements the existing `CacheProvider`. It is optional and non-authoritative. Authorities use it for federation fetch caching and validated Resolve snapshots; it never participates in transactions. Protect the cache against unauthorized writes: Resolve signs responses from these stored assessments.

Use a shared cache when processes should reuse remote Entity Configurations or statements. Resolve snapshots are isolated to each authority instance. After cache loss or restart, authenticated requests or local `resolveEntity()` calls can warm them; anonymous requests return `not_found` until a matching assessment is available. See [Resolve discovery and caching](7.3.resolve-endpoint.md#resolve-cache-and-signed-response-lifetimes).

Cache TTLs are durations in seconds. `Clock.now()` returns NumericDate seconds since the Unix epoch, as do replay expiry, subordinate timestamps, and trust-mark timestamps.

## Keys

Federation key lifecycle remains separate from storage. A database may hold public key metadata and KMS references internally, but `RotatingKeyring` is the package contract that exposes signing, active federation JWKS publication, rotation, retirement, revocation, and historical federation keys.

Never place private JWK material in `StorageAdapter` or published federation JWKS.

The authority package exports the storage contracts and `MemoryStorageAdapter`. Its nested in-memory repository implementations are internal.

## Production checklist

- [ ] Each adapter binds its repositories to one logical authority namespace.
- [ ] One adapter object owns the authority's configured storage capabilities; protocol-role stores are configured separately.
- [ ] Authority transactions are serializable and roll back atomically.
- [ ] Subordinate cursors and ordering are deterministic.
- [ ] Trust-mark expiry, revocation history, and exact-JWT lookup are preserved.
- [ ] Replay claims are atomic and namespaced by issuer and audience.
- [ ] Replay failures fail closed.
- [ ] Cache is treated as disposable, non-authoritative data.
- [ ] All authoritative state is shared across deployment processes and survives restarts.
- [ ] Federation signer custody remains behind `RotatingKeyring`.

## Subordinate events

`subordinateEvents` is an optional history repository scoped by authority issuer and subordinate subject. Authorities advertising the Subordinate Events endpoint require it. Configure the memory implementation with `new MemoryStorageAdapter({ subordinateEvents: true })`.

The [`SubordinateEventStorage` reference](../api/authority/storage.md#subordinateeventstorage) lists the current methods, parameters, and return types. Implement that exported contract rather than maintaining a local copy.

`SubordinateEvent` comes from `@oidfed/core`. Events use numeric epoch seconds in `iat`, an extensible `event` string, and optional `event_description` and `information_uri`. Preserve supplied occurrence times and append order, including ties and repeated event types. Return detached values. Capture nested event values before the first asynchronous wait, including before a queued transaction begins. A caller must not be able to mutate persisted events through input objects or returned values. The memory adapter and authority manual-recording API both take this snapshot.

Keep history independent of the current subordinate row. Removing that row must not delete events, and re-registration extends its existing history. Do not backfill from `createdAt` or `updatedAt`, silently prune records, or truncate responses. Durable retention and issuer/subject isolation are responsibilities of the production adapter.

Automatic capture occurs through `registerSubordinate`, `updateSubordinate`, and `revokeSubordinate`. Registration and updates snapshot caller inputs before waiting for a transaction. Their callbacks use transaction-bound repositories and commit state and generated events together. An events-enabled adapter must supply `tx.subordinateEvents`; otherwise the authority fails before mutation. Rollback and serialization retries must leave no changes from failed attempts.

Direct storage writes remain untracked. Applications using them can explicitly append in the same transaction:

Only record `revocation` when the removal represents an actual revocation. Technical cleanup alone does not establish that meaning. The transaction callback may run again after a conflict; keep signing and network operations outside it.

Adapters may implement `readSnapshot(callback)` to provide a consistent read-only view of subordinate records and event history. The Events endpoint uses it when available and otherwise uses `transaction`. Read methods return detached values. Callbacks use the supplied view; calling a write method on the adapter from inside the callback can deadlock a serialized implementation. The memory adapter serializes reads with writes and copies only the requested records.

Automatic capture follows the Draft 01 event definitions literally: `metadata_policy_update` tracks `metadata_policy`. Changes solely to `metadata_policy_crit` or `constraints` generate no standard event. A framework can record a custom event for those changes under [Subordinate Events §2.3.3](https://openid.net/specs/openid-federation-subordinate-events-1_0-01.html#section-2.3.3).

## Collection snapshots

Entity Collection stores snapshots separately from subordinate registration records, using the core `EntityCollectionStore` contract. The service uses `collection.store` when supplied, then `storage.collections`, then its own memory store. Enable the storage capability with `MemoryStorageAdapter({ collections: true })`.

The service publishes each snapshot atomically after collection, outside registration transactions. A store shared across instances must isolate anchors, retain snapshots and opaque cursors, enforce expiry, and return detached values. See [Entity Collection](14.2.collection-operations.md#refresh-and-storage).

Collection entries have an `expiresAt` eligibility deadline and may also carry `chainExpiresAt` evidence. Custom collectors do not need to provide chain evidence. Core derives the mark evidence used for filtering during refresh. Keep these internal fields separate from the public entity data when persisting snapshots.

### Transaction callbacks and snapshots

Commit all writes made through the supplied transaction repositories together, or roll them all back when the callback fails. Use only those repositories inside the callback. Calling a queued parent mutation and awaiting it there can deadlock: the parent write waits for the transaction that is waiting for that write.

A read snapshot must give the callback one consistent view and return detached records. Its callback must not await writes through the parent adapter either. Implementations may hold a read boundary for the callback or provide an independent snapshot; applications should not depend on one particular locking mechanism.

`listCandidates()` intentionally includes revoked and expired records. Current-validity queries apply eligibility before choosing the newest record, so a newer mark with an expired delegation cannot hide an older eligible one. Full signature, profile, and issuer verification remain separate checks.

## Shared storage and key contracts

The authority's [`StorageAdapter`](../../packages/authority/src/storage/types.ts) stores subordinate records and any configured Trust Mark, event, collection, replay, and cache data. Configure OIDC registrations and sessions, wallet protocol state, and role-specific replay stores through their [OIDC](15.1.oidc-roles.md#provider-replay-and-persistence-hooks) and [wallet](16.5.wallet-attestation-verification.md#wallet-attestation-verification-details) integration points. Attaching a role to a host does not connect all of that role's state to authority storage.

Production adapters must meet oidfed's [storage contracts](11.6.storage-adapters.md): isolate authority namespaces, return detached records, and provide serializable transactions with atomic commit and rollback. The transaction API and these adapter guarantees are library contracts. The specifications do not prescribe a database technology.

Client assertions require `exp`, `jti`, and one-time use unless reuse was negotiated. These requirements come from [OIDC Core §9](https://openid.net/specs/openid-connect-core-1_0.html#ClientAuthentication), referenced by [Federation §8.8](https://openid.net/specs/openid-federation-1_0.html#section-8.8). oidfed enforces one-time use through its [replay contract](#replay-protection). The store must claim identifiers atomically across processes serving the same receiver, retain them through the accepted expiry and clock-skew window, and fail closed on backend errors. This store design is an oidfed contract.

Under oidfed's [key-provider contract](9.4.federation-keys.md#providers-publication-checks-and-key-history), the provider is responsible for private-key custody and lifecycle state. Production providers must persist that state and coordinate the processes signing and publishing for one entity. Lifecycle providers retain historical public keys separately from the current JWKS.

Publishing a Historical Keys endpoint is optional under [Federation §8.7](https://openid.net/specs/openid-federation-1_0.html#section-8.7). If you publish one, its response and historical-key fields follow [§8.7.2](https://openid.net/specs/openid-federation-1_0.html#section-8.7.2). The bundled [rotating memory keyring](../api/crypto/migration.md#publish-and-retire-keys-deliberately) and memory stores lose state on restart and do not coordinate across processes.

Federation Entity Keys `SHOULD NOT` be used for other protocols under [Federation §3.1.1](https://openid.net/specs/openid-federation-1_0.html#section-3.1.1). [§5.2.1](https://openid.net/specs/openid-federation-1_0.html#section-5.2.1) separates protocol-role keys from top-level federation keys. If you publish multiple protocol JWK Set representations, [§5.2.1.1](https://openid.net/specs/openid-federation-1_0.html#section-5.2.1.1) says their keys `SHOULD` be the same and implementations `MUST` make them consistent in a timely manner.

oidfed provides distinct keyring purposes for federation and protocol signing. Hosts schedule protocol-key rotation; managed roles derive their JWKS from the same purpose snapshots used for signing. See the [crypto migration guide](../api/crypto/migration.md).
