# 3. Trust chains

[Feature guides](README.md)

**LIGO Wiki** receives signed evidence about **Umeå University OP**. Before using it, **LIGO Wiki** checks the path to one of its configured anchors and the metadata that follows from that path. [Federation §4](https://openid.net/specs/openid-federation-1_0.html#section-4).

Use the host's `discoverEntity()` for online discovery or `discoverEntityFromChain()` for supplied statements. For registration and Wallet requests, the role operation adds its protocol checks to that federation validation.

## Follow one trust decision

LIGO Wiki starts with its own configured anchors and either a supplied chain or a discovery request for Umeå. The validator authenticates the statements, checks their links and constraints, and applies Superior metadata and policy. The accepted result binds effective metadata to a particular path and expiration.

That result is the input to a later protocol operation. An RP can use the validated OP endpoint; a wallet can continue the verifier-request checks appropriate to its role. Neither application should switch back to values copied from an unverified configuration because they are more convenient.

If several paths are available, select among the candidates eligible for the operation. If evidence is expired or rejected, stop that dependent action and refresh or repair the configuration. Keep the failed result visible to the operator without exposing signed proofs or confidential application data in user-facing errors.
